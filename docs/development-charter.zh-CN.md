# Kura 开发规范与项目宪章

本文定义 Kura 的开发原则、日常开发流程、测试流程、测试用例编写要求和提交规范。所有新功能、修复、重构和文档变更都应遵守这份规范。

## 项目宪章

Kura 是一个面向 NAS 场景的动漫优先媒体自动化系统，核心目标是让 RSS 获取、订阅策略、下载、整理、元数据修复、数据健康检查和浏览器播放变得可检查、可回滚、可长期维护。

### 核心原则

- 透明优先：任何自动化文件移动、订阅匹配、AI 判断和元数据修复都必须留下用户可以理解的状态、原因或审计线索。
- 安全优先：所有文件操作必须限制在配置允许的根目录内；整理操作默认先生成计划，再由用户或明确策略执行。
- 动画优先：动画命名、季度、集数、字幕组、清晰度、编码和语言版本是产品的一等领域模型，不能退化成普通文件名字符串处理。
- 本地可运行：每个可交付变更都应能通过本地开发环境验证，不能只依赖部署环境。
- 小步提交：每次变更应有清晰边界，避免把无关重构、格式化、功能修改和文档更新混在同一次提交中。
- 测试随行为走：修改解析、匹配、整理、下载、API、数据库迁移或用户工作流时，必须补充或更新相应测试。

### 决策边界

- 产品行为优先服从 `docs/kura-product-baseline.md` 中的定位、视觉和领域约束。
- 部署、本地运行和环境变量以 `docs/deployment.md` 为准。
- 涉及订阅策略、历史补番、整理安全的改动，应先阅读对应设计文档，避免破坏已有领域假设。
- 真实 API key、aria2 secret、NAS 主机名、NAS IP、私有仓库名和真实家庭路径不得提交。

### Agent 指令入口

- `AGENTS.md` 是 Codex 和兼容 agent 的项目级自动指令入口。
- `CLAUDE.md` 是 Claude Code 的项目级自动记忆入口。
- 这两个文件只保留高频、硬性、可执行的项目规则；完整制度和解释以本文为准。
- 修改开发流程、测试要求或提交规范时，应同步检查 `AGENTS.md` 与 `CLAUDE.md` 是否需要更新。

## 开发流程

### 1. 开始前

1. 同步最新代码，确认工作区状态：

   ```bash
   git status --short
   ```

2. 阅读与任务相关的现有实现、测试和文档。优先使用 `rg` 定位领域代码、API 路由和测试。
3. 明确改动类型：
   - 功能：新增用户可见能力或 API 行为。
   - 修复：修正错误行为、边界条件或回归。
   - 重构：不改变行为，只改善结构。
   - 测试：新增或调整测试覆盖。
   - 文档：更新说明、设计或运维流程。

### 2. 本地环境

首次开发：

```bash
cp .env.example .env
npm install
npm run prisma:migrate:dev
```

启动 Web：

```bash
npm run dev
```

启动 worker：

```bash
npm run worker
```

默认访问：

```text
http://localhost:3000/zh-Hans
```

如果使用 Docker Compose，本地全栈启动以 `docs/deployment.md` 为准。

### 3. 实现要求

- TypeScript 类型应表达真实领域含义，避免用宽泛的 `any`、隐式字符串协议或重复的魔法常量。
- 输入边界必须校验。API route、环境变量、外部 RSS、aria2 回包、AI 回包和用户提交内容应通过明确 schema 或 helper 归一化。
- 文件路径必须做根目录约束和路径穿越防护，不能直接信任数据库、RSS、AI 或请求里的路径。
- 数据库 schema 变更必须配套 Prisma migration，并说明兼容性影响。
- UI 改动应保持 Kura 的暗色 NAS 控制台风格：信息密度高、控件克制、图像承担主要氛围，不新增营销式页面。
- 多语言文案变更必须同步检查英文、简体中文、繁体中文入口，避免只改一个 locale。
- 后台任务应幂等，重复执行不能制造重复下载、重复计划或不可恢复的文件状态。
- AI 能力只能作为辅助判断，不得绕过现有安全 gate；低置信度或高风险结果必须进入审核流程。

### 4. 完成定义

一个任务只有在以下条件满足后才算完成：

- 行为实现与需求一致，边界条件被考虑。
- 对应测试已新增或更新。
- `npm run lint`、`npm run test` 和必要时的 `npm run build` 已通过，或明确记录不能运行的原因。
- 用户可见流程已在本地页面、API 或命令层验证。
- 文档、环境变量示例或部署说明已按需更新。
- `git status --short` 中只包含本任务相关改动，或已明确说明哪些是无关既有改动。

## 测试流程

### 必跑检查

常规变更提交前运行：

```bash
npm run lint
npm run test
```

涉及 Next.js 页面、API route、Prisma、Docker、运行时配置或打包行为时额外运行：

```bash
npm run build
```

涉及数据库迁移时运行：

```bash
npm run prisma:migrate:dev
```

涉及后台任务时，至少本地启动 worker 并验证目标 job 不会重复创建副作用。

### 分层测试策略

- 领域纯函数：使用 Vitest 单元测试覆盖解析、归一化、分组、排序、诊断和状态计算。
- API route：测试状态码、输入校验、错误结构、权限或安全边界、数据库读写副作用。
- 数据库行为：测试 schema 变化、迁移默认值、唯一约束和查询条件。
- 文件整理：测试 dry-run、目标路径生成、冲突处理、根目录限制、拒绝危险路径。
- 下载与 RSS：测试外部回包的正常、缺字段、重复、失败和脏数据情况。
- UI 工作流：重要页面至少做本地手动验证；交互复杂或回归风险高时补充组件或端到端测试。

### 测试数据原则

- 测试输入应接近真实动画资源命名，包括多语言标题、季度、集数、字幕组、清晰度、编码和特殊集。
- 外部服务不可作为单元测试依赖。RSS、aria2、AI 和元数据服务都应使用 fixture 或 mock。
- 测试不得读写真实 NAS 路径。临时目录必须可控、可清理。
- 测试用例名称要描述业务行为，而不是只描述函数名。

## 测试用例开发规范

新增测试文件应靠近被测代码：

```text
src/lib/anime-parser.ts
src/lib/anime-parser.test.ts
```

推荐结构：

```ts
import { describe, expect, it } from "vitest";

describe("parseAnimeReleaseTitle", () => {
  it("keeps season and episode identity when subtitle tags are noisy", () => {
    // arrange
    // act
    // assert
  });
});
```

### 每个用例应包含

- 明确场景：输入来自哪个用户流程或外部系统。
- 明确期望：断言业务结果，不只断言非空。
- 至少一个风险点：错季、错集、路径越界、重复下载、错误自动执行、外部脏数据等。
- 失败可读性：断言对象应尽量稳定，避免依赖无关字段顺序。

### 必须补测试的情况

- 修改 `src/lib/*` 中的解析、匹配、整理、下载、字幕、元数据、订阅或队列逻辑。
- 修改 `src/app/api/**` 中的请求输入、响应结构、状态码或数据库副作用。
- 修改 Prisma schema、环境变量读取、路径构造或安全校验。
- 修复 bug。测试应先表达 bug 的失败场景，再验证修复结果。
- 新增用户工作流。至少覆盖核心成功路径和一个失败或边界路径。

### 可以不补测试但要说明原因的情况

- 只改文档、注释、截图或纯文案。
- 只改不会影响行为的样式细节。
- 临时诊断改动，且不会提交到主分支。

## 提交流程

### 提交前检查清单

1. 查看改动范围：

   ```bash
   git diff --stat
   git diff
   ```

2. 确认没有提交敏感信息：

   ```bash
   git diff -- . ':!package-lock.json'
   ```

3. 运行必要检查：

   ```bash
   npm run lint
   npm run test
   npm run build
   ```

4. 查看最终状态：

   ```bash
   git status --short
   ```

### Commit 规范

提交信息使用英文 Conventional Commits：

```text
feat: add subscription candidate review queue
fix: reject organizer paths outside data root
test: cover anime episode identity conflicts
docs: add development charter
refactor: simplify wanted episode coverage builder
chore: update build tooling
```

常用类型：

- `feat`: 新功能或用户可见能力。
- `fix`: bug 修复或行为回归修复。
- `test`: 测试新增或调整。
- `docs`: 文档变更。
- `refactor`: 不改变行为的结构调整。
- `chore`: 工具链、依赖、构建或维护任务。

提交原则：

- 一次提交只表达一个主题。
- 不把格式化全仓和业务改动混在一起。
- 不提交 `.env`、真实媒体库路径、下载缓存、数据库文件或生成的本地运行噪声。
- 如果检查未完整运行，提交说明或 PR 描述中必须写明原因和风险。

### PR 或合并说明

提交后的合并说明应包含：

- 变更摘要。
- 测试结果，包括实际运行的命令。
- 数据库迁移、环境变量、部署或回滚注意事项。
- 用户可见行为截图或本地验证方式，适用于 UI/工作流变更。

## 例外处理

紧急修复可以先缩小验证范围，但必须满足：

- 修复范围足够小。
- 至少运行与风险直接相关的测试。
- 合并后补齐完整测试和文档。
- 说明为什么跳过了完整检查。

任何会自动移动、删除、覆盖媒体文件的变更，不适用紧急跳过规则；必须先验证 dry-run、安全边界和可回滚路径。
